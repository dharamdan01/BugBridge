## Workflow and architecture

`scripts/reproduce-bug.mjs` imports the existing `createApp()` factory and creates an in-process HTTP server bound only to `127.0.0.1`, using port `0` so the OS selects an available port. It does not import the production server entrypoint, consult its configuration, or contact an existing API server. Each app owns a new service and private Map. Only the fixed synthetic baseline task is created; no tasks are updated or deleted. Existing application instances and their task data remain independent.

The runner uses built-in Node.js `fetch`, five-second request deadlines and disabled redirects. It creates a valid control task, then sends `{}` as JSON and a POST with no body or Content-Type header. Each response is parsed from real HTTP. Fixture `actual` values are never used as evidence. A final GET verifies the control task is unchanged and no invalid creation inserted a task; another GET verifies health.

`withTemporaryApi()` wraps startup and all HTTP work in `try/finally`, awaits server closure and closes active sockets even on exceptions or request timeout. Reports are written only after closure succeeds. Tests verify the server is no longer listening and subsequent connections fail, including cleanup on thrown operations, malformed responses and stalled requests. File-write failure is also tested after server closure.

`collectEvidence()` separates verified HTTP observations from source-based analysis and human-review recommendations. `runReproduction()` writes both `reports/phase9-bug-evidence.json` and `reports/phase9-bug-evidence.md`; importing the module does not run its CLI or write files.

The report uses schema version 1, incident ID INC-001, bug ID BUG-001, an actual ISO reproduction timestamp and relative source paths. Request metadata comes from fixed synthetic inputs. Responses retain only allowlisted fields: HTTP status, JSON content-type check, success flag, safe error code/message and detail count, plus validated synthetic baseline task fields. Unknown strings are redacted. Arbitrary response fields, headers, error details, exception messages, stack traces and process configuration are excluded. Privacy tests inject a synthetic secret into real local responses and verify it is absent from both generated formats.

## Code-supported analysis and suggested fix

The route is mounted in `src/app.js`; `src/routes/tasks.routes.js` dispatches POST `/` to `createTasksController(service).create`. In `src/controllers/tasks.controller.js`, lines 12–16 explicitly throw a generic Error for undefined bodies or empty objects. This happens before `validateTaskInput(req.body)` at line 18. The validator in `src/validation/tasks.validation.js` already rejects non-objects and missing titles with HTTP 400 VALIDATION_ERROR. Express forwards the generic exception to `src/middleware/error-handler.js`, whose lines 27–32 map non-HttpError exceptions to the sanitized HTTP 500 INTERNAL_ERROR response.

The smallest proposed fix is to remove that intentional throw branch and let the existing validator handle both cases, then remove the unused `isObject` import. This is a recommendation only. No controller, validator, error handler, fixture or existing regression assertion was changed. Generic-error sanitization should remain intact.

## Limitations and future human approval

- Scope is the known empty-task-creation incident in a fresh in-memory instance. This is not production traffic capture or persistence verification.
- Only two representations of empty POST input are exercised; broader API coverage remains in the existing normal suite.
- Evidence is a sanitized projection, not a raw HTTP dump. Unexpected codes/messages are redacted and fail the acceptance check; they are never substituted with the known bug's values.
- Reports are local generated files and not automatically sent to Mattermost. Review their timestamp before asking the agent to investigate.
- A startup/protocol/cleanup failure can prevent a new report; a file-write failure can leave partial or older report files. Writes are not transactional across the pair. The CLI exits 1 and warns about stale timestamps; treat reports as current only after an exit-0 reproduction run. Abrupt process termination is outside normal `finally` cleanup guarantees.
- The existing separate regression deliberately remains red. There are no unexpected test failures or sandbox verification blockers.
- This workspace has no Git repository metadata, so preservation was checked using file hashes rather than a Git diff. Nothing was pushed or deployed; no dependency was added.

In Phase 10, present the evidence and smallest proposed patch to a human for explicit approval. Only after approval should a separate editing workflow implement the fix. Keep chat execution read-only. Then require the unchanged regression to pass with 400 VALIDATION_ERROR for both cases, valid creation to remain 201, rejected requests to leave storage unchanged, and normal API/Switch/smoke suites to pass. Update the reproduction acceptance policy for the approved fixed state as part of that later phase. No approval service or automatic patching is implemented here.
